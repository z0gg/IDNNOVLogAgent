# IDNNOV Log Agent — Contexte projet (mémoire projet, pas Hermes global)

> Mémoire durable du projet Synology IDNNOV Log Agent. Injectée automatiquement
> dans chaque session Hermes ouverte sur ce workspace. Mettre à jour ce fichier
> après chaque découverte structurante, publication ou changement de convention.
> Aucun secret ici : les identifiants viennent de Bitwarden SM (projet hermes).

## Identité

- **Produit** : IDNNOV Log Agent (SPK Synology natif) — reçoit les logs DSM de
  Log Center sur `127.0.0.1:5514` (TCP RFC 5424) et les pousse en HTTPS vers
  OpenObserve self-hosté (`https://logs.idnnov.com`, Coolify, v0.92.2).
- **Dépôt** : `github.com/z0gg/IDNNOVLogAgent` (branche main).
- **Catalogue public** : `packages.idnnov.com` (Cloudflare Pages, projet
  `idnnov-package-catalogue`, Worker `repository/src/worker.mjs`).
- **Cible** : flotte >100 NAS clients AMD/Intel, DSM 7.2–7.4 (build 72806+).
- **Modèle multi-compagnie** : 1 organisation OpenObserve = 1 compagnie
  (ex. Laroche, ID org `3IpSzrDn5K5UpPiprhpEXsmj3bR`), 1 stream commun
  `synology_logs` par org, champs `idnnov_company` / `idnnov_nas` /
  `idnnov_device_id` (UUID stable survivant aux repairs) sur chaque événement.
  Aucune valeur compagnie codée en dur dans le SPK.
- **Jamais de stream `default`** : s'il a été supprimé, OpenObserve répond
  « stream is being deleted » (HTTP 400) et les tests d'auth retournent un 401
  trompeur pendant la purge.
- **Jamais de reboot NAS** pour une installation de paquet (dernier recours
  uniquement). Réparation > réinstallation : `synopkg install <spk>` conserve
  `var/etc` (settings + token + device_id).
- Propriétaire : Rock Langlois (z0gg). Français, exécution autonome vérifiée,
  preview avant publication, secrets jamais en clair dans le chat.

## Cause racine synoscgi DSM 7.2 (validée sur VM réelle, version 1.1.6-1021)

Le bug UI « Apply n'enregistre rien » (502 `upstream prematurely closed`)
venait de trois comportements synoscgi, prouvés par expérimentation sur
VirtualDSM 7.2.2 :

1. **Aucun body POST n'est transmis aux CGIs de paquet.** Tout CGI qui lit
   stdin reste bloqué jusqu'au kill par DSM → 502 nginx. L'API de l'app est
   donc strictement GET (paramètres en query string), jamais de lecture stdin.
2. **Le CGI démarre en root SANS les variables `SYNOPKG_*`** (ni
   `SYNOPKG_PKGDEST`, ni `SYNOPKG_PKGVAR`) → `settings.json` (mode 0700, appartenu
   au user du paquet) illisible, crash silencieux. Le wrapper `bin/api.cgi`
   re-définit `PYTHONPATH`, `SYNOPKG_PKGDEST`, `SYNOPKG_PKGVAR`,
   `SYNOPKG_PKGNAME` puis redescend vers le user du paquet via
   `setpriv --reuid … --regid … --clear-groups` quand root.
3. **Pas de `REMOTE_USER`.** L'identité de session s'obtient en exécutant
   `/usr/syno/synoman/webman/modules/authenticate.cgi` depuis le CGI : synoscgi
   lui transmet les cookies de session (`id` + `did`) et il renvoie rc=0 + le
   nom d'utilisateur. rc=5 = pas de session valide.

Mot de passe d'ingestion : jamais en clair. L'UI appelle `action=nonce`
(nonce à usage unique, TTL 300 s, `var/etc/nonces.json` 0600), masque le
secret par XOR+base64 avec le nonce, le CGI démasque après avoir consommé le
nonce. Toujours préférer HTTPS (5001) en production.

**Leçon de debug** : un login Playwright par formulaire DSM échoue en silence
(champ password caché anti-autofill, decoys) et fait conclure à tort que
`authenticate.cgi` est mort. Pour tester : `POST /webman/login.cgi?logout=1`
(API officielle, renvoie `id`/`did`) exécuté dans le contexte de page.

## Historique des versions structurantes

- **1.0.8-1009** : suppression `conf/resource` (`usr-local-linker` rejeté au
  `prepare_start` → erreur 272). Règle : ne déclarer une ressource qu'après
  preuve `readelf`.
- **1.0.9-1010** : `Format octet_counting` (DSM Log Center envoie du RFC 6587
  sur TCP, préfixe `<longueur> `).
- **1.0.10-1011** : `Time_Strict Off` (DSM omet les millisecondes, `%L` strict
  rejetait les timestamps).
- **1.0.11-1012** : icônes PACKAGE_ICON 64/256 ; miniatures catalogue via
  `thumbnail`/`thumbnail_retina` (le Package Center lit le catalogue, pas
  l'icône embarquée, pour la liste Communauté).
- **1.1.0-1013 → 1.1.5-1018** : modèle multi-compagnie, IDs d'org
  case-sensitifs, preset OpenObserve (gzip, mapping Host/Port/URI/Basic),
  save-before-test, stream `synology_logs` par défaut.
- **1.1.6-1021** (publiée GitHub + catalogue + CI verte, md5 `b633e5bc…`) :
  fix UI Apply — cause racine synoscgi ci-dessus. Chaîne validée de bout en
  bout sur VM : UI → Appliquer → `fluent-bit.conf` régénéré → OpenObserve
  HTTP 200.
- **1.1.6-1022** : X-SYNO-TOKEN sur tous les appels UI→CGI + strip
  `\n`/espaces des tokens (UI, CGI, persistence, bootstrap). Premier NAS
  réel (GRLAROCHE-SRV) : UI + ingestion 200.
- **1.1.7-1023** (publiée, sha256 `dff57cab…`, upgrade GRLAROCHE-SRV fait
  manuellement par le user) : **Timezone fix** — Fluent Bit 5.0.9 jette
  l'offset UTC quand `Time_Format` combine `%L` et `%z` (événements indexés
  avec l'heure locale lue comme UTC → décalage du fuseau entier, logs
  invisibles dans les fenêtres temporelles de l'UI OpenObserve). Correctif :
  `Time_Format %Y-%m-%dT%H:%M:%S%z`, prouvé sur banc d'essai Fluent Bit réel
  (13:20:22-04:00 → 17:20:22 UTC). Test de régression dans `test_package.py`.
  Vérifié en prod : événements NAS avec retard 8–12 min seulement.

- **1.1.9-1026** (publiée, sha256 `e4d0e6cb…`) : **simplification assumée** — l'application
  desktop est supprimée (pkgroot/ui retiré, INFO sans dsmuidir/dsmappname). L'assistant
  d'installation (URL, org, compagnie, stream, nom du NAS, identifiants) est l'interface
  unique; après installation l'agent tourne sans interface. Le user préfère cette simplicité
  (pas d'icône de menu, pas de bouton Ouvrir). Vérifié VM : install/upgrade OK, running,
  ingestion continue. Ne PAS réintroduire d'UI desktop.

## Analyse OpenObserve par l'agent (patron multi-clients)

- 1 organisation OpenObserve = 1 client ; 1 stream `synology_logs` par org.
- L'agent lit les logs via un **Service Account org-scoped en lecture**
  (Basic `user:pass`) : secrets dans Bitwarden sous `OO_HERMES_<client>`
  (ex. OO_HERMES pour Laroche, id `23da782a-14d2-48b6-ad3d-b4bb01194eb0`,
  valeur = `user:pass` en clair ou base64).
- **API** : l'org se référence par son **identifiant interne case-sensitive**
  (forme longue type `3IpSzrDn…`), PAS par le nom d'affichage (`laroche`
  → 401). Endpoints : `GET /api/<org>/streams`,
  `POST /api/<org>/_search` (SQL, `start_time`/`end_time` en
  **microsecondes** obligatoires). Ingestion : `POST /api/<org>/synology_logs/_json`.
- Onboard client type : créer l'org OO + SA lecture → secret BW
  `OO_HERMES_<client>` → installer SPK (catalogue) avec org/stream/user du
  client → vérifier via API que les événements arrivent avec `_timestamp` correct.

## Procédures clés

- **Build** : `python3 scripts/build.py --fluent-bit build/fluent-bit-final2/bin/fluent-bit`
  → `artifacts/IDNNOVLogAgent-<v>-x86_64.spk` (+SHA256SUMS). Bump version par
  sed dans `scripts/build.py`, `spk/INFO`, `src/idnnov_agent/api.py`, `tests/`.
- **Publication** : commit → release GitHub (API REST avec PAT via
  `bws secret get`, gh CLI absent) → vérifier hash public re-téléchargé →
  maj `repository/catalog/releases.json` (md5/sha256/size/url/changelog) →
  tests worker → `npm run build` → commit → deploy
  `npx wrangler@latest pages deploy pages-dist --project-name
  idnnov-package-catalogue --branch main --commit-hash <sha>` → vérifier
  production sur les 2 matrices (r1000/build 72806/DSM 7.2 +
  geminilake/build 90080/DSM 7.4, paramètre `language` obligatoire).
- **Git push** : `GITHUB_TOKEN=$(bws…) GIT_ASKPASS=… git push` (HTTPS + token).
- **Diagnostic NAS** : `synopkg status`, `tail var/fluent-bit.log`,
  `netstat -lnt | grep 5514`, curl Basic avec le token côté serveur, jamais
  le token affiché en clair.
